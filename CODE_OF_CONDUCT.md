# Code of Conduct

## Our Commitment

We want this project to be a respectful, educational, and technically honest place for collaboration.

Contributors, reviewers, maintainers, and users are expected to communicate professionally and help keep discussions focused on the work.

---

## Expected Behavior

Examples of positive behavior include:

- Being respectful and patient.
- Critiquing ideas and code, not people.
- Explaining technical disagreements with evidence.
- Stating uncertainty instead of pretending.
- Keeping contributions within the approved task scope.
- Giving credit for the work of others.
- Welcoming beginners while preserving engineering quality.
- Reporting limitations and failing tests honestly.
- Asking questions when requirements are unclear.
- Helping discussions remain focused and useful.

---

## Unacceptable Behavior

The following behavior is not acceptable:

- Personal attacks.
- Harassment or intimidation.
- Discriminatory or insulting comments.
- Publishing another person's private information.
- Deliberately misleading claims about project readiness.
- Hiding failing tests or known limitations.
- Claiming that unimplemented features are working.
- Repeatedly ignoring task boundaries after review feedback.
- Disruptive behavior that prevents useful technical discussion.
- Using the project to promote unrelated products or services.
- Pressuring contributors to share private credentials, files, or access.

---

## Technical Integrity

Contributors must not:

- Fake simulator behavior from the frontend.
- Hide unsupported MMIO access.
- Mark tests as passed when they were not executed.
- Remove failing tests only to make a pull request pass.
- Add large dependencies without explaining why.
- Expand task scope without approval.
- Claim compatibility that has not been verified.
- Commit secrets, credentials, or private user data.

Technical disagreements should be resolved using:

- Official documentation.
- Reproducible tests.
- Small feasibility experiments.
- Architecture decisions.
- Clear acceptance criteria.

---

## Scope and Collaboration

The project follows a small-task workflow.

Contributors are expected to:

1. Work on one approved task at a time.
2. Respect the task's non-goals.
3. Avoid unrelated refactoring.
4. Include test results.
5. Document known limitations.
6. Accept review feedback professionally.
7. Ask before changing architecture or scope.

---

## Reporting Problems

Conduct concerns should be reported privately to the repository owner when possible.

Do not use public issues to expose:

- Sensitive personal information.
- Private messages.
- Security details.
- Credentials or account information.

When reporting a concern, include:

- What happened.
- Where it happened.
- Relevant links or screenshots.
- Whether the behavior is ongoing.
- Any immediate safety or access concerns.

---

## Enforcement

Repository maintainers may:

- Edit or remove inappropriate comments.
- Close or lock disruptive discussions.
- Reject contributions that violate project rules.
- Temporarily restrict participation.
- Permanently block users in serious or repeated cases.

Enforcement decisions should be based on the behavior and its impact on the project community.

---

## Project Principle

Respect, honesty, and technical accuracy are required.

The project should progress carefully without misleading users, contributors, or reviewers about what is currently implemented.
